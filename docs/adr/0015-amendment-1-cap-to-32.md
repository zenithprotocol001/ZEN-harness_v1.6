# ADR-0015-amendment-1: Cap → 32 for v1.5.0

- **Status:** accepted
- **Date:** 2026-09-08
- **Amends:** ADR-0015 (capability whitelist, v1.4.0)
- **Supersedes:** the cap of 24 in ADR-0015 §"The cap"

## Context

ADR-0015 set a v1.4.0 capability cap of 24 (current surface = 20, headroom
= 4). v1.5.0 adds six new capabilities (`BRANCH_CREATE`, `BRANCH_SWITCH`,
`BRANCH_LIST`, `ATTACHMENT_PUT`, `ATTACHMENT_GET`, `ATTACHMENT_DELETE`),
bringing the surface to 26, which exceeds the cap.

Three options were considered:

1. **Raise the cap to 32** (this amendment). Keeps the fine-grained
   auditability of the per-capability entry. Headroom of 6 for the
   v1.5.x window.
2. Split the release (branching in v1.5.0, attachments in v1.5.1)
   to stay ≤ 24 per release. Loses the ability to ship a coherent
   data model; forces a per-release panic over the cap.
3. Coarsen the new capabilities to 4 (e.g. `branch.read/write`,
   `attachment.read/write`). Tight fit to 24. Loses per-operation
   audit granularity in the Entropy Map and the test generator.

## Decision

The cap is **32** for v1.5.0. The original cap of 24 is preserved
as a frozen archaeology constant: `CAPABILITY_BUDGET_V140 = 24` is
not deleted. The new constant is `CAPABILITY_BUDGET_V150 = 32`.

```python
CAPABILITY_BUDGET_V140: int = 24   # archaeology; not raised
CAPABILITY_BUDGET_V150: int = 32   # v1.5.0 cap
```

The cap is enforced by `scripts/invariants_check.ps1` as a
*property check*, not only by the module-load `assert` in
`capabilities.py`. The property check runs against the loaded
`Capability` enum and fails with a clear message:

```
FAIL: v1.5.0 cap exceeded: len(Capability) = N, cap = 32
```

## Why 32 and not 24 (the audit)

The cap exists to force a conscious scope decision when a new
feature would exceed it. The cap value itself is a guide, not a
constraint: the *constraint* is the process (every bump requires
an ADR, an Entropy Map row, and a generated test case). 32 admits
the v1.5.0 surface (26) plus 6 headroom for v1.5.1 follow-ups
(auto-forwarding, attachment listing, branch pruning) without
forcing a mid-release ADR.

The cap does not become "the current release + a fudge factor."
Each future bump must argue for itself in a new amendment that
names the new capabilities and the headroom it consumes.

## What does NOT change in this amendment

- The CREC principle: every capability still requires an ADR
  entry, a whitelist row, a `@requires` decorator on a C1 route,
  and a pass/deny test case (generated by
  `enumerate_capability_tests`).
- The bijection invariant: `set(Capability) == ACTION_WHITELIST.keys()
  == web_core.registered_capabilities`. The amendment adds 6
  values, 6 routes, 6 whitelist entries, 6 test cases. The
  invariant still holds by construction.
- The default-deny rule and the per-capability error type
  (`CapabilityDenied`).

## Consequences

- The Entropy Map (`docs/entropy-map.md`) grows from 20 to 26
  rows. The new rows are `branch.*` (3) and `attachment.*` (3).
- The test count grows by ~18 pass/deny cases for the 6 new
  capabilities (3 per capability: pass, deny, raise). The exact
  count is determined by the generator, not by hand.
- A future bump (e.g. ADR-0015-amendment-2 for v1.6.0) must
  follow the same shape: state the reason, name the new
  capabilities, name the headroom consumed.
